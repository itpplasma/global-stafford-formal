# Global Stafford v1.0.3

Fixes a Lean module-name collision in Palomar submission. The generic `Challenge` and `Solution` names resolved to the Stafford38 dependency's files, so Comparator could not find `GlobalStaffordChallenge.universalStatement`. The failed run's machine report records both incorrect paths in `docs/verification/failures/palomar-34287264858.json`.

The configuration now selects `GlobalStaffordChallenge` and `GlobalStaffordSolution`. Their source bytes preserve the original frozen statement and solution; the theorem, proof mathematics and dependency pins are unchanged. A source-resolution gate checks Lake's actual search path before every verifier run. The transport consumer imports the uniquely named Challenge.

Palomar's own resolver reproduced the old collision and selected the correct root files with the new names. Phase I and full verification pass against AlgebraicAnalysis v0.3.0 and Stafford38 v1.1.0. Both standard and Palomar canonical-Challenge comparisons passed Comparator, NanoDa and Lean. The canonical replay used the upstream compiler and Landrun adapter; only its unavailable outer systemd wrapper was omitted locally. Full evidence is in docs/verification-results.json.

For Palomar, use the full v1.0.3 release commit, `comparator.json`, `formalization.yaml`, and the repository root. The existing failed submission's commit cannot acquire this fix; submit the new commit.
